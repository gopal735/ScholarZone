# ADR-001: Free-first PostgreSQL hosting for ScholarZone

Status: **accepted for implementation; production cutover blocked** (the
Neon production project is quota-exhausted and no verified production
backup exists — see "Current blockers").
Date: 2026-10-12.
Scope: the hosted PostgreSQL database and the hosting topology around it.
The application, its models, and its public catalogue snapshot are
unchanged by this decision; the point is where the bytes live when the
operator's PC is off.

## Context

ScholarZone's backend is SQLAlchemy + FastAPI, deployed to Vercel, with a
PostgreSQL database on Neon. The production Neon project
(`noisy-voice-39538737`, branch `br-weathered-river-ayi29isd`) currently
refuses every connection with the provider's quota error — verified on
2026-10-12 from GitHub Actions runners (all endpoints) and corroborated by
the production API answering `503 {"detail":"Database unreachable"}`. The
requirement is a hosting arrangement that keeps the site, the admin CRUD
and the backups working with the operator's PC off, on free tiers only,
with proven restore.

## Constraints found in the repository (measured, not assumed)

- `backend/app/models.py` uses only portable SQLAlchemy types (`JSON`,
  `Text`, `Numeric`, `DateTime`, …). No `pgvector`, no Postgres-only column
  types.
- Dialect-specific behaviour (UPSERT, DDL) is already abstracted:
  `maintenance_slot_store` chooses `postgresql_insert` vs `sqlite_insert`
  per dialect; `supervisor_ddl.create_table_statements(dialect)` carries
  both dialect bodies; `image_audit.audit_ddl_for(dialect)` likewise.
- `app/database.py` rewrites a bare `postgresql://` URL to
  `postgresql+psycopg://`, connects with TLS required and SSL-mode
  enforcement for PostgreSQL, and validates the schema on boot.
- The public catalogue is served from a committed static snapshot
  (`frontend/public/scholarships-snapshot.json`, 618 records, generated by
  the repo's own generator) with a documented service fallback for API
  outages — free-first architecture from PRs #34/#35.
- Backups: `.github/workflows/database-backup.yml` produces encrypted,
  transfer-budgeted backups of an allow-listed source. It has never run,
  and its allow-list repository variable is unset.

## Options compared (limits verified against official pricing pages on 2026-10-12)

| | **Supabase Free** (chosen) | **Aiven Free** | CockroachDB |
|---|---|---|---|
| Cost | $0 | $0 | **no free tier** — 30-day trial with $400 credit, then pay-per-vCPU-hour (Cockroach Continuum, Sep 2026 pricing) |
| PostgreSQL | full PostgreSQL; "a Supabase project can be used as a standalone Postgres database… any Postgres client or ORM" | full PostgreSQL, 1 dedicated VM | CRDB wire protocol — **not** PostgreSQL; SQLAlchemy dialects differ (no true `JSONB`/`GENERATED` parity, different UPSERT semantics) |
| Storage | 500 MB | 1 GB | — |
| Availability rule | **paused after 1 week of inactivity** | may be shut down "if unused for an extended period" (AUP) | clusters pause after the trial |
| Free projects | 2 | 1 | — |
| Egress | 5 GB included | included | metered |
| Automatic backups | not included on free | "single backup only for disaster recovery" on free | managed backups on paid |
| Region choice | yes | no (free cannot select cloud/region) | yes |
| Direct connection for pg_dump/restore | yes (pooler and direct) | yes | yes |

Also considered and rejected: **Cloudflare D1 / Turso** (SQLite, not
PostgreSQL — incompatible with the schema's `SERIAL/GENERATED` DDL and the
UPSERT dialect code without a rewrite); **Vercel Postgres** (a resale of
Neon — the very provider whose free-tier quota is the current blocker);
**Oracle Always Free / AWS RDS free tier** (12-month or always-free tiers
exist but the account setup is heavier than the project warrants and RDS's
free tier is time-limited).

## Decision

**Supabase Free, two projects**: `prod` (application) and `backup-restore`
(the disposable restore target the backup verification restores into).
Rationale:

1. **Zero schema compromise.** It is real PostgreSQL; every
   portable-typed model and every dialect branch in the repository keeps
   working. The alternatives either cost money or change the dialect.
2. **The 500 MB limit is not a constraint** — the application's data
   volume is a few thousand small rows (the local reference database has
   ~700 scholars and the whole public snapshot is 8 MB of JSON, most of it
   prose in fields that would be far smaller in a database).
3. **Two free projects cover the required architecture** exactly: one
   production, one non-production restore target where a backup can be
   proven without touching production.
4. The free tier's one sharp edge — **inactivity pause** — is answered by
   the repository's other free resource: the `database-keepalive.yml`
   workflow runs a read-only `SELECT 1` weekly, and the public catalogue
   already serves from the static snapshot during any database outage.

## Consequences

- **New configuration surface**: `SCHOLARZONE_DATABASE_URL` (already the
  only setting the app reads) points at Supabase's pooler for the app and
  at the direct connection for `pg_dump`/`pg_restore`/the keep-alive.
  Credentials live only in the host's secret store, exactly as today.
- **A backup is not optional and not self-attesting.**
  `scripts/pg_backup.py` dumps with `pg_dump --format=custom`, gzips,
  SHA-256s, restores into an **empty** scratch database and refuses to
  emit the artifact unless the restore succeeded and the scratch was
  empty first. `scripts/restore_drill.py` runs the whole procedure monthly
  in `restore-drill.yml` against a throwaway PostgreSQL service container
  — a green drill is evidence about the procedure.
- **The pause response is a documented procedure, not an outage**: the
  keep-alive failing means "restore the project from the dashboard", and
  the static catalogue keeps serving meanwhile.
- **Free-tier limits that bound the design**: 500 MB (monitor), 5 GB
  egress (the public catalogue is served from the static snapshot on
  Vercel/Netlify, so the database serves the API, not the catalogue), and
  the inactivity pause. Backup transfer is budgeted by the existing
  encrypted-backup workflow's monthly-MiB variable so saving the database
  cannot take the project's quota down.

## Migration and cutover plan (NOT executed)

1. **Provision**: create the Supabase free projects; record the pooler and
   direct connection strings in the host's secret store only.
2. **Schema**: `init_database()` creates the schema through the repo's own
   DDL path on the empty project (drill-verified).
3. **Data**: only from a **verified** backup of the current production
   database — which requires the Neon quota block to be lifted and a dump
   taken with the procedure above, restored into the `backup-restore`
   project, with table row counts reconciled against the source. A local
   SQLite file or the empty recovery project is not a source.
4. **Cutover**: update the `SCHOLARZONE_DATABASE_URL` secret to the
   Supabase pooler; redeploy; verify `/api/health`, the catalogue, and the
   admin endpoints against the new host. The static snapshot does not
   change during cutover — it is already independent of the database.
5. **Decommission Neon** only after the Supabase host has served a full
   cycle with a verified backup of its own.
6. **Rollback**: point `SCHOLARZONE_DATABASE_URL` back at the (still
   existing, quota permitting) Neon project and redeploy. The public
   snapshot is unaffected in both directions.

## Current blockers

1. **Production database access**: Neon quota-exhausted (verified
   2026-10-12; exact provider error text in the run log of the read-only
   audit workflow). Until it is lifted, no production dump exists and
   therefore no production migration can be parity-verified.
2. **No verified restorable production backup**: the backup workflow has
   never run and its allow-list variable is unset. The new
   `scripts/pg_backup.py` + `restore-drill.yml` make the procedure real
   and tested, but a *production* dump remains a separately authorised
   action.
3. **Approval**: provisioning accounts, setting secrets, and the
   production cutover are operator decisions; nothing here deploys.

## What this ADR does not claim

- It does not claim production data parity: the drill proves the
  procedure, not the data, and says so in the workflow header.
- It does not claim the Neon outage is permanent or that the provider is at
  fault: the quota error is a resource condition, reversible by the owner.
- It does not change billing, add services, or deploy anything.
