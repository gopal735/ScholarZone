## Phase 3: Environment Variables

The application requires these environment variables in production:

### Required
- `SCHOLARZONE_DATABASE_URL` — PostgreSQL connection string (auto-set by Render)
- `SCHOLARZONE_VERIFICATION_SECRET` — Secret for verification endpoint (auto-generated)
- `SCHOLARZONE_ADMIN_SECRET` — Secret for admin image review endpoints (auto-generated)

### Optional but Recommended
- `SCHOLARZONE_ALLOWED_ORIGINS` — Comma-separated list of allowed CORS origins
- `RESEND_API_KEY` — For email notifications
- `NOTIFICATION_EMAIL` — Email address for notifications

### Validation in start.sh

The `start.sh` script validates:
1. `SCHOLARZONE_DATABASE_URL` must be set
2. In production, `SCHOLARZONE_DATABASE_URL` must NOT be SQLite
3. Warning if `SCHOLARZONE_VERIFICATION_SECRET` is not set

If validation fails, the application will NOT start.

## Phase 4: PostgreSQL Database

### Fail-Safe Mechanism

The application has multiple layers of protection:

1. **start.sh validation**: Rejects SQLite in production
2. **config.py**: Falls back to SQLite default only if env var is missing
3. **Render Blueprint**: Auto-sets `SCHOLARZONE_DATABASE_URL` from the managed database

### If SCHOLARZONE_DATABASE_URL is Missing

The application will:
1. `start.sh` exits with error before starting
2. `config.py` falls back to SQLite default (local development only)
3. Tests use `sqlite:///:memory:` or temp files

**Production will NOT silently start with an empty SQLite database.**

## Phase 5: Data Migration

### Migration Files Created

| File | Description |
|------|-------------|
| `migration_export.sql` | PostgreSQL-compatible SQL with all data |
| `migration_validate.py` | Validation script for SQLite and PostgreSQL |
| `migration_validation.sql` | SQL queries to verify PostgreSQL after migration |

### Migration Steps

#### Step 1: Get PostgreSQL Connection String

After Render PostgreSQL is provisioned, get the connection string from:
- Dashboard → scholarzone-db → Connect → Internal Connection String

Format: `postgresql://user:host:password@host:5432/dbname`

#### Step 2: Create Schema

The application creates the schema on first startup. After the first deployment:
1. Access the Render Web Service shell
2. Run:
   ```bash
   python -c "from app.database import init_database; init_database()"
   ```

#### Step 3: Import Data

**Option A: Using psql (Recommended)**

```bash
# Download the migration SQL
# From your local machine:
psql "postgresql://user:password@host:5432/dbname" -f migration_export.sql
```

**Option B: Using Render Shell**

1. Go to scholarzone-api → Shell
2. Copy the contents of `migration_export.sql`
3. Run:
   ```bash
   psql $SCHOLARZONE_DATABASE_URL -f /path/to/migration_export.sql
   ```

**Option C: Programmatic Migration**

```bash
python migration_export.py --target postgresql://$SCHOLARZONE_DATABASE_URL
```

## Phase 9: Enable Scheduled Verification (GitHub Actions)

**ONLY AFTER ALL PREVIOUS PHASES PASS**

The autonomous verification trigger is provided by a GitHub Actions scheduled
workflow. It runs every 12 hours and calls the existing
`POST /internal/verify/trigger` endpoint.

### Required GitHub Repository Settings

1. Go to your GitHub repository → **Settings** → **Secrets and variables** → **Actions**
2. Create the following **Repository secret**:

   | Name | Description |
   |------|-------------|
   | `SCHOLARZONE_VERIFICATION_SECRET` | Must match the `SCHOLARZONE_VERIFICATION_SECRET` value configured in Render for `scholarzone-api`. Generate a strong random string (e.g., `openssl rand -hex 32`). |

3. Create the following **Repository variable**:

   | Name | Description |
   |------|-------------|
   | `SCHOLARZONE_API_URL` | Public HTTPS URL of the deployed Render web service (e.g., `https://scholarzone-api.onrender.com`). |

### Verify the Workflow

The workflow file `.github/workflows/verification-cron.yml` is already present in
the repository and configured with:

- **Schedule**: `7 */12 * * *` (runs at 00:07 and 12:07 UTC daily)
- **Manual trigger**: `workflow_dispatch` available in the GitHub Actions UI
- **Overlap protection**: `concurrency` group `verification-trigger` with `cancel-in-progress: true`

To manually test before relying on the schedule:

```bash
# In GitHub repository → Actions → ScholarZone Verification Trigger → Run workflow
```

Or from a local shell (replace with your actual values):

```bash
curl -sf -X POST "https://your-api.onrender.com/internal/verify/trigger" \
  -H "X-Verification-Secret: your-secret-here"
```

Expected response: `202 Accepted`

### Troubleshooting

If the workflow fails:

1. Verify `SCHOLARZONE_VERIFICATION_SECRET` is set in GitHub repository secrets
2. Verify `SCHOLARZONE_API_URL` is set in GitHub repository variables
3. Confirm the secret value matches the Render environment variable for `scholarzone-api`
4. Check the Render web service is running and reachable
5. Review GitHub Actions run logs for HTTP response codes
